10. THE GAME MUST ACTUALLY FEEL LIKE A PUZZLE
==================================================

The current gameplay is too easy.

Right now the user can click almost any vehicle and eventually finish the level.

THIS MUST BE FIXED.

This is a puzzle game.

The player should need to look at the board and think:

"Which vehicle should I move first?"

"Which color should go first?"

"What is blocking this vehicle?"

"If I move this one, what will become available next?"

The order of moves should matter.

Create situations where:

- One vehicle blocks another.
- A vehicle cannot leave because another object is in front of it.
- Some vehicles should be moved before others.
- Color choice matters.
- Spool state matters.
- Available slots matter.
- Vehicle orientation matters.
- Space must sometimes be cleared.
- The player must observe before tapping.

The gameplay must NOT simply be:

Tap all cars → Level Complete

The puzzle should contain meaningful decision-making.

14. VEHICLE BLOCKING
==================================================

When the player selects a vehicle:

1. Determine its intended movement direction.
2. Check the actual physical path in front of it.
3. Determine whether another vehicle/object blocks the path.
4. If blocked, prevent it from passing through.
5. Play blocked/invalid feedback.
6. If the reference shows it, move slightly toward the obstacle and return.
7. If the path is clear, allow movement.

The blocking system must detect partial obstruction.

For example:

If only approximately 10% of another vehicle is physically overlapping the moving vehicle's required path, it should still count as blocked if collision would occur.

Do NOT only check one center ray or the exact center of a row/column.

Use the best appropriate solution, such as:

- Physics.BoxCast
- Physics.OverlapBox
- Bounds checks
- Multiple raycasts

depending on the game architecture.

Do not run expensive checks continuously every frame for every vehicle.

Run them when needed.

49. VEHICLE OPTIMIZATION
==================================================

Reuse:

- Vehicle meshes
- Prefabs
- Materials
- Textures

Do not duplicate models simply because their colors differ.

Avoid unnecessary unique material instances.

Where suitable use:

MaterialPropertyBlock

or carefully shared materials.

Be aware that:

renderer.material

can create separate material instances.

Do not accidentally create dozens of duplicated materials.

==================================================
50. MATERIAL / DRAW CALL OPTIMIZATION
==================================================

Reduce material variation where possible.

Prefer:

- Shared materials
- Texture atlases
- Sprite atlases
- GPU instancing
- Static batching where appropriate
- Simple shaders

Do not combine interactive objects blindly.

Only batch/combine objects where it makes sense.

==================================================
51. SHADERS
==================================================

Use mobile-friendly shaders.

Avoid unnecessarily expensive:

- Multi-pass shaders
- Realtime reflections
- Complex transparent shaders
- Excessive shader calculations
- Heavy post-processing

If a simpler shader provides nearly the same appearance, use the simpler one.

==================================================
52. LIGHTING
==================================================

Keep lighting attractive but efficient.

Prefer:

- Simple main directional lighting
- Ambient lighting
- Baked lighting where useful
- Minimal realtime lights

Avoid numerous realtime lights affecting multiple objects.

==================================================
53. SHADOWS
==================================================

Use shadows carefully.

Optimize:

- Shadow distance
- Resolution
- Shadow casters
- Shadow receivers

Tiny decorative objects and small yarn pieces normally should not need expensive realtime shadows unless they materially improve appearance.

==================================================
54. PARTICLE OPTIMIZATION
==================================================

Particles should remain lightweight.

Do not use thousands of particles for tiny feedback.

Use short controlled bursts.

Particle systems should normally:

Activate
↓
Play
↓
Finish
↓
Stop
↓
Deactivate/reuse

Do not leave unnecessary particle systems continuously simulating.

==================================================
55. UI PERFORMANCE
==================================================

Avoid unnecessary Canvas rebuilds.

Do not frequently rebuild permanent UI.

Avoid excessive use of:

- ContentSizeFitter
- LayoutGroups
- Dynamic hierarchy changes
- Full-screen transparent overlays
- Constant layout recalculation

Separate frequently changing elements from mostly static UI if beneficial.

==================================================
56. PHYSICS PERFORMANCE
==================================================

Do not execute expensive physics queries every frame for every vehicle.

Prefer:

User selects vehicle
        ↓
Perform required path check
        ↓
Use result
        ↓
Check again only when needed

Use simple colliders where possible:

- BoxCollider
- SphereCollider
- CapsuleCollider

Avoid expensive MeshCollider where a simple shape works.

==================================================
57. UPDATE() PERFORMANCE
==================================================

Avoid unnecessary Update() methods.

Static or event-driven objects do not need to run logic every frame.

Be particularly careful with:

- Every yarn segment
- Every slot
- Every UI image
- Every decorative object
- Every particle helper

Prefer centralized or event-driven updates where suitable.

==================================================
58. OBJECT POOLING
==================================================

Use pooling where frequent reuse makes sense.

Candidates include:

- Thumbs-up feedback
- Particle bursts
- Temporary feedback
- Yarn segments if repeatedly recreated
- Other frequently spawned objects

Avoid excessive runtime:

Instantiate()
Destroy()

during normal gameplay.

==================================================
59. TEXTURE OPTIMIZATION
==================================================

Review texture sizes.

Do not use huge textures for very small mobile-screen objects unless required.

Optimize:

- Max Size
- Compression
- Sprite Atlas
- Texture Atlas
- Mip Maps where appropriate

Maintain good visual quality while reducing memory and rendering cost.

==================================================
60. OVERDRAW
==================================================

Watch overdraw, especially with portrait mobile UI.

Avoid excessive overlapping transparent elements.

Pay attention to:

- Full-screen transparent images
- Large transparent particles
- Multiple overlapping UI layers
- Transparent environment materials

Use Unity rendering/debugging tools where useful.

==================================================
61. TARGET 30 FPS
==================================================

The minimum performance target is:

30 FPS.

Frame-time budget:

approximately 33.3 ms.

Do NOT use 60 FPS as the hard requirement for this project.

If the game runs above 30 FPS, that is good.

However, it must at minimum be designed to maintain a stable 30 FPS target during normal intended gameplay.

Focus on smooth and consistent performance rather than unstable high FPS.
